Zero-Knowledge Delivery Model

Obsidian Secure enforces strict mathematical confidentiality. The server acts purely as an encrypted blob store.

01

Local Key Generation

Cryptographically secure 256-bit AES keys and unique initialization vectors (IVs) are generated locally in browser memory via the Web Crypto API. Plaintext keys are never transmitted.

02

In-Memory Ciphertext

Payloads are encrypted chunk-by-chunk in client RAM before initiating HTTP uploads. The backend storage system receives and persists solely encrypted ciphertext blobs.

03

Fragment Hash Delivery

Decryption keys are passed strictly within the URL fragment hash (#key=...). RFC standard HTTP clients never transmit fragment parameters to servers.

Security Architecture FAQ

Detailed explanations of the cryptographic trust boundary.

Why is no recipient account required?

Decryption is performed directly in the recipient browser via JavaScript Web Crypto. Because the decryption key is located strictly in the URL hash fragment, the recipient scripts decrypt data locally without user accounts or server authentication.

Can the server decrypt stored files or read messages?

No. Payloads are encrypted with AES-256-GCM before transmission. The URL hash fragment containing the key is never sent over HTTP request headers, making server-side plaintext recovery mathematically impossible.

What happens when a share link expires?

Once the expiry timestamp elapses, the backend rejects all access requests with HTTP 410 Gone. An automatic storage cleanup process purges expired ciphertext binary files from the disk volume.

How does instant file revocation work?

Senders can revoke any active transfer from their Active Shares dashboard at any time. Revocation immediately invalidates the database token and irreversibly removes the encrypted disk files.
