Zero-Knowledge Delivery Model

Obsidian Secure implements browser-side cryptography, isolating encryption keys from server systems.

1

Local Generation

An AES-GCM 256-bit key is generated directly in your browser's memory using the Web Crypto API. The plaintext key never leaves your local system.

2

Encrypted Uploads

Files are encrypted in-memory before upload. Only the ciphertext payload is uploaded over TLS to the storage directory.

3

Hash Delivery

The key is appended to the URL fragment hash (#key=...). Because browsers do not transmit fragments to servers, keys remain strictly client-side.

Engineering & Systems Architecture

Obsidian Secure is built as a highly optimized, production-ready portfolio project featuring modern engineering primitives.

memory

Client Cryptography

Processes payloads up to 100 MB directly in browser memory. Utilizes AES-256-GCM single-request encryption to secure your assets without browser tab crashes or memory leakage.

database

Metrics Batch Buffering

Includes a thread-safe batch buffering layer that queues download notifications and flushes metrics periodically. Reduces heavy disk I/O operations and prevents database lockouts under concurrent workloads.

shield

Production Hardening

Designed with strict security headers, including HTTP Strict Transport Security (HSTS) and granular Content Security Policies (CSP). Safe WSGI reverse proxy configurations ensure client IP validity for rate limiters.

Security & Architecture FAQ

Review key cryptographic design decisions behind Obsidian Secure.

Why is no recipient account required?

Decryption occurs on-the-fly in the recipient's browser. Since the decryption key is passed via the URL's hash fragment, the recipient's local scripts decrypt the raw bytes without registering accounts or logging in.

Can forgotten passwords be recovered?

No. To maintain strict zero-knowledge isolation, your master password is used to generate session keys. The database stores password hashes but cannot recover them. Forgotten passwords result in complete loss of E2EE shares.

What happens when files expire?

Upon expiration, files are immediately marked as offline. A daemon script executes in the background of the application context, securely deleting orphan binary files from the storage volume.

Can the host server decrypt my files?

No. Files are encrypted with AES-GCM 256-bit encryption before upload. The server never receives the hash fragment representing the key, meaning the host is physically incapable of decrypting payloads.

How does file revocation work?

Senders can instantly revoke any active share link from their Active Shares ledger. Revocation immediately purges the database metadata and deletes the encrypted payload from disk storage.
